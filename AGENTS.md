## What Is This Project?

OmAgents is a multi-host agent toolkit with explicit OpenCode (`@omagents/omagents`), Codex (`@omagents/omagents-codex`), and DeepSeek Harness (`@omagents/omagents-dsh`) packages plus shared `@omagents/core` capabilities. Core is an automatic dependency, not a separate user install. The approved host installs are `npx @omagents/omagents`, `npx @omagents/omagents-codex`, and `dsh plugin --profile web add @omagents/omagents-dsh`; neither npm installer takes a host positional argument.

├─────────────────────────────────────────────────┤
│  Infrastructure Layer (bundled: OmAgents)        │

├─────────────────────────────────────────────────┤
│  OpenCode · Codex · DeepSeek Harness runtimes    │

- **OmAgents** = infrastructure layer. Provides tools and capabilities.
- **Superpowers** = process skills layer. Provides development workflows.
- **User choice layer** is NOT bundled. OmAgents stays neutral on methodology.

## Plugin Entry Point (`packages/opencode/src/index.js`)

The repository's `.opencode/plugins/index.js` is only a development re-export of this packaged implementation.

The default export is a **dual V1/V2 descriptor** (same pattern as superpowers >= 6.4):

```js
export default { id: "omagents", server: OmagentsPlugin, setup: setupV2 }
```

- **V1 (opencode 1.x)**: calls `server()` (>= 1.18.29) or scans the named `OmagentsPlugin` export (older). `server()` returns the V1 hooks object. Note V1 hosts may also invoke `default.setup` with a V1-shaped ctx — `setupV2` detects this (missing `ctx.session.hook`/`ctx.skill.transform`) and returns quietly.
- **V2 (opencode 2.x)**: reads `id` + `setup()` and never calls `server()`. `setupV2(ctx)` registers everything through the V2 plugin context: skills via `ctx.skill.transform`, MCP servers via `ctx.mcp.transform`, `/ps` command via `ctx.command.transform`, tools via `ctx.tool.transform`, PATH injection via `ctx.shell.hook("create.before")`, job board + system prompt via `ctx.session.hook("context")`, compaction note via `ctx.session.hook("compaction")`, lifecycle via `ctx.event.subscribe()`.

No `@opencode/plugin` import — the descriptor is a plain object, keeping the package dependency-free and loadable by both runtimes.

**Self-repo dedup guard:** when OpenCode runs inside the OmAgents source repo itself, the repo's `.opencode/plugins/*.js` are auto-discovered as project plugins *on top of* any globally-installed `@omagents/omagents`. The published (node_modules) copy detects this (project `package.json` name + project-local `.opencode/plugins/index.js`, walking up from `ctx.location.directory` on V2 / `ctx.directory` on V1) and yields, so the local working-tree checkout is the single active copy. Never remove this guard — without it everything registers twice in this repo. Note: `opencode plugin list` is a static inventory of *loadable* modules and still lists all entries (npm + local + parallel-engine); the guard only prevents the npm copy's `setup()`/`server()` from activating. (Project `opencode.json` with `"plugin": []` does NOT disable globally-configured plugins — the arrays merge — so a config-level fix is not possible.)

On load the plugin:

1. **Load superpowers** through `getCorePaths().superpowersDir` with graceful degradation; `loadSuperpowers()` resolves both halves (`server` for V1, `setup` for V2) without relying on npm hoisting
2. **Register skills** (V1: OmAgents and upstream Superpowers directories through `config.skills.paths`; V2: Core discovery/rendering plus per-skill `ctx.skill.transform` for all 33 skills). V2 retains the upstream Superpowers bootstrap but suppresses its separate file-based registration. Core supports exactly `opencode-v1`, `opencode-v2`, `codex`, and `dsh`; `SKILL.md` is the fallback and `SKILL.<host>.md` is a full-content override. Superpowers rendering replaces every `docs/superpowers` documentation root with `docs` for arbitrary following subdirectories; V1 injects the equivalent path preference into its system prompt, and existing documents are not migrated automatically
3. **Register MCP servers** (V1: `config.mcp` with `enabled`; V2: `ctx.mcp.transform` with the `enabled` key stripped). User config takes precedence (won't override existing)
4. **Merge hooks** from superpowers + parallel execution engine (V1)
5. **Provision the persistent Python base** at `~/.venvs/omagents` through `packages/core/hooks/python-env.js`, auto-installing only missing core packages (`jinja2`). V1 runs on `session.created`; V2 runs at plugin setup, non-blocking. Uses `node:child_process`, runs once per process, and never auto-deletes the base. Project overlays are created separately on demand, never at plugin startup.
6. **Inject PATH** via shell hook: venv bin + skill script dirs + existing PATH (deduped)

Key variables:
- `getCorePaths()` = Core `root`, `skillsDir`, `superpowersDir`, `hooksDir`, `mcpCatalogPath`, `searchProxyDir`, and `searchProxyEntry`, resolved from `import.meta.url` and Core's own dependency resolver. Superpowers explicitly prefers the real workspace/app-hoisted installation, falls back to Core's bundled nested dependency, and stays stable across prepack/postpack cleanup. Only `superpowersDir` is optional and becomes `null` when that dependency is absent; other asset failures remain visible
- `SKILLS_DIR` = `getCorePaths().skillsDir` in the OpenCode adapter
- `AGENT_VENV` / `AGENT_VENV_BIN` = persistent base path and its platform-specific executable directory, defined in `packages/core/hooks/python-env.js`
- `getProjectVenvPath(projectRoot)` = `<project-root>/.omagents/venv`, the on-demand project overlay
- `SKILL_SCRIPT_DIRS` = script directories from deep-research, markitdown-converter, playwright-web-scraping, _shared beneath Core's skill root

## Standalone Codex Installer (`packages/codex/`)

- `npx @omagents/omagents-codex` installs Codex with no arguments; `--help` and `--version` are the only supported options, and unknown arguments fail.
- `src/setup.js` exports `installCodex(options?)` and `serializeTomlBasicString(value)`. It resolves hooks and assets through `getCorePaths()`, renders skills through Core for the `codex` host, and serializes `resolveMcpServers()` without duplicating MCP selection or tool mappings. In `auto`, it copies all six self-contained `search-proxy` modules into the plugin cache and passes the copied absolute `index.mjs` as the resolver's explicit entry override; the generated `.mcp.json` never references the source checkout, Core's npx cache, or a package-dependency path. Provider and credential configuration is an install-time snapshot: set the environment before installation, rerun the installer after changes, and restart Codex with that environment. Marketplace paths are valid escaped TOML basic strings. Bearer serialization is scoped by MCP server owner: `github` uses `bearer_token_env_var = "GITHUB_TOKEN"`, while direct `youdotcom` uses `bearer_token_env_var = "YDC_API_KEY"` rather than serializing its Bearer secret. Exa and Keenable headers, automatic local Proxy `env` (including configured `YDC_API_KEY`), and Context7 stdio environment values remain in `.mcp.json` because the plugin contract has no equivalent indirection, so private directories use mode `0700` and `.mcp.json` uses mode `0600` on POSIX-mode platforms. Reinstallation refreshes the copied Proxy and replaces stale provider entries and credentials.
- Codex retains native subagents and does not load the OpenCode parallel engine. There is no root dispatcher, legacy `.codex/` implementation, or compatibility command.

## DSH Host and Web Client Bundle (`packages/dsh/`)

- The package-root Host module has named `name = "omagents"`, `inject = ["loader"]`, async `apply(ctx)`, `createDshRuntime(ctx)`, `createSubagentTracker(ctx, board, health?)`, `OmAgentsRemote`, `authorizeRemoteScope`, `registerDshSkills`, `registerDshMcp`, `provisionDshPython`, `registerDshTools`, `registerDshCommands`, and `registerDshContext` exports; it has no default or Client export. The React Client is available only through the separate `./client` export.
- `createDshRuntime()` opens Core's `JsonJobStore` at `$DSH_HOME/profiles/<active-profile>/omagents/job-board.json`, using the Loader `baseUrl` to identify the active profile and `@deepseek-ai/dsh-home-paths` for home resolution. DSH's host-local degrading store preserves the current in-memory Board and Remote list/watch/reconciliation after read/write/flush failures while exposing persistence diagnostics. Save admission is serialized in the DSH adapter so every adapter-queued save re-checks degradation before entering Core's write queue; flush/close drain that adapter queue. Runtimes sharing a profile also share the write queue and latest revision, preventing an older overlapping runtime from replacing a newer Board snapshot. A degraded runtime stops current and future disk writes so an unreadable startup store or newer repaired snapshot cannot be overwritten; reopen it after repair to restore durability. Core's sticky failure contract is unchanged for other hosts. Host, persistence, tracking, skills, MCP, Python, tools, commands, and context health records remain independent; disposal flushes and closes the Board, unregisters capabilities, and prevents late Python completion from mutating health.
- `registerDshSkills()` renders Core definitions for the explicit `dsh` host and registers exactly 18 OmAgents + 15 Superpowers skills through `ctx.skills.register()`. Registrations use the rendered instruction body, absolute selected paths, and directory `resourceBase` values resolved from Core rather than cwd; their composed disposer invalidates native discovery. If the registry is not yet available, a Cordis-injected capability fiber waits for it and activates/reactivates without blocking Host or Python; disposal prevents late registration. Full DSH overrides exist for `parallel-execution`, `deep-research`, `hyperplan`, `doctor`, and `lsp-guide`; every DSH skill uses native `subagent` semantics without OpenCode launch arguments or `OPENCODE_` variables. DSH tool rendering maps automatic generic Proxy tools to `mcp__websearch__search`/`mcp__websearch__fetch`, explicit Exa web tools to `web_search`/`web_fetch`, Keenable tools to `mcp__keenable__search_web_pages`/`mcp__keenable__fetch_page_content`, You.com tools to `mcp__youdotcom__you-search`/`mcp__youdotcom__you-extract`, codegraph to `mcp__codegraph__codegraph_explore`, and GitHub calls to `mcp__github__*`, while shared skills retain their native OpenCode/Codex forms through explicit host rendering. All 33 DSH skills also receive absolute packaged script/Core-hook/base-Python resource resolution (including Superpowers script paths); they never assume cwd-relative `scripts/`, bare loop/research CLIs, or source-checkout paths. Bare packaged-script commands and sibling-skill script paths resolve to normalized absolute files only when those files exist, preserving command arguments, hypothetical examples, legitimate prose, and already absolute paths. Model-tool mappings are distinct from CLI text, so `officecli load_skill <name>` remains unchanged while the standalone model action maps to native `skill`.
- `createSubagentTracker(ctx, board, health?)` observes typed native `tools/result`, `subagent/start`, and `subagent/end` events, correlating activation results and runs by parent session and durable child session ID. DSH 0.2.2-rc.2+ activation results carry only the model-facing child `name`, so the tracker resolves it to the durable child id with `ctx.subagents.resolveName(caller, name, exec.signal)`, resolving the name/`subagentId`/`childId` identity before correlating; lifecycle events supply the durable creator through `info.parentSessionId`. It maps `completed`/`aborted`/failure stop reasons idempotently, recovers native `interrupted` Session outcomes as `interrupted` rather than cancellation, treats native settlement delivery as injected without duplicate notices, backfills equivalent-terminal details, and reconciles active jobs from live Agents or readable Session outcomes without inferring success from inactivity. Cancellation uses DSH 0.2.2-rc.3's `ctx.subagents.interrupt(childId, { kind: "user" })` admission API (the parent is derived from the calling context, not passed in the authority): acceptance alone enters `cancelling`, while only authoritative settlement marks `cancelled`. Local interruption preserves descendants; external one-shot runs cannot resume. Delayed tools/subagent activation, startup reconciliation deferred until live-Agent and Session-query capabilities are also available, orphan end-before-result correlation, racing native ends, missed starts, and repeat-safe listener disposal preserve durable Board state; observed active external runs remain active on cold session-not-found. Listener, subscription, activation-name resolution, and recovery failures degrade independent tracking health, and successful reactivation/query clears the corresponding diagnostic.
- `registerDshTools(ctx, board, tracker, health?)` uses DSH `defineTool` for read-only `parallel_status` and idempotent `cancel_task` canonical JSON/output declarations. Unknown, terminal, and repeated cancellations return current job state without duplicate Host interrupts. `registerDshCommands()` registers direct human `/ps`, returning Core `buildPsText` without creating a model prompt/message. `registerDshContext()` contributes the automatic Superpowers `using-superpowers` bootstrap, DSH-native tool mapping, and native subagent instructions through `systemPrompt.section`, plus a required, freshly assembled state-preservation + scoped Board snapshot through `systemPrompt.context`. Only pending outcome IDs actually rendered into a parent's snapshot become `injected`; native `agent/turn-stopping` acknowledges that parent's injected outcomes so later turns do not repeat recovered notices. Native settlement retains direct `injected` semantics and per-parent isolation. Top-level sessions receive the controller bootstrap without per-session opt-in; sessions whose real `session.header.origin` is `subagent` retain native skills and parallel guidance without restarting controller workflows (there is no direct `session.origin` accessor). Native DSH `skill` tooling supplies the live 33-entry catalog, and the React-creation acceptance route must load `brainstorming` before product code. `refreshContext` restores required context after compactable history is removed. Tools, commands, and systemPrompt each use delayed-capability activation/reactivation with repeat-safe composed disposal, and projection failures degrade only context health without rejecting model assembly.
- `new OmAgentsRemote(ctx, { board, tracker, health, authorizeScope })` extends `TypertRemoteService` as the `omagentsRemote` Cordis service with wire namespace `omagents` (distinct from `ctx.omagents`). Its Remote methods are `listJobs(scope)`, `cancelJob(jobId)`, `getHealth()`, and stream `watchJobs(scope, signal)`; `JobScope` accepts only an optional `parentSessionId`, and the active-profile Board remains the outer isolation boundary. `authorizeRemoteScope` evaluates DSH session resources through the invocation-derived Context and `ctx.remoteAccess.allows()`, while unscoped reads filter every job and denied explicit scopes/jobs throw structured `remote-access/denied` errors. Unknown jobs and failed cancellation admission use `omagents/job-not-found` and `omagents/cancel-failed`. Cancellation returns the current Board record after admission (normally `cancelling`) and never fabricates settlement. `listJobs` and each initial/reconnect watch baseline reconcile only authorized active jobs; cold Remote queries defer until live-Agent and Session-query capabilities are available. Every watch attaches the Core listener synchronously before reconciliation and its whole-set baseline, retains/coalesces later frames through the latest revision without further native polling, and starts a fresh baseline on reconnect. Its iterator wrapper closes/wakes/detaches synchronously on `return()`/`throw()` even during initial reconciliation or a pending `next()`; abort, iterator `finally`, and service disposal remain repeat-safe, with no periodic polling or use of DSH's application forwarded-event source.

Viewing details never acknowledges a model notification. The React UI provides all/running/attention/finished filters, complete execution/notification/detail states, confirmed non-repeatable cancellation, and loading/empty/stale/permission/degraded presentations. ## Parallel Execution Engine (`packages/opencode/src/parallel.js`)

The parallel execution engine:

- **V1**: intercepts `task` tool calls with `background: true`; auto-enables background subagents by writing `OPENCODE_EXPERIMENTAL_BACKGROUND_SUBAGENTS=true` to shell config
- **V2**: intercepts native `subagent` tool calls (always background in current OpenCode, with no `background` argument or env var); the child session ID comes from the tool result's structured `metadata.sessionID` (text parsing as fallback); completion notices arrive as synthetic `<subagent sessionID="..." state="...">` user messages scanned by the `context` hook; `sessionID` follow-up rounds remain native-only so historical notices cannot reactivate terminal Board records; `session.idle` / `session.execution.{succeeded,failed,interrupted}` events are the completion/fallback/reconcile path; cancel uses `ctx.session.interrupt`
- Maintains Job Board (`Map<taskID, JobRecord>`), persisted to `~/.local/share/opencode/storage/omagents/job-board.json`
- Injects Job Board status into LLM context (V1: `experimental.chat.messages.transform`; V2: `ctx.session.hook("context")`); sentinel-guarded against double injection
- Injects parallel execution system prompt (V1: `experimental.chat.system.transform` with `task(...)`; V2: `event.system` with `subagent(...)`)
- Provides custom tools: `parallel_status`, `cancel_task`
- Registers `/ps` command (V1: `config.command`; V2: `ctx.command.transform`, skipped if the user defined their own `ps`)
- Writes TUI state to `~/.local/share/opencode/storage/omagents/tui-state.json`
- Its default export is a `{ id, server, setup }` descriptor too (V2 auto-discovery requires object defaults); `setup` is a deliberate no-op — the real wiring is done by `index.js` via the named exports

## MCP Servers

Registered automatically (V1: `config` hook; V2: `ctx.mcp.transform`). User config takes precedence (won't override existing). `OMAGENTS_SEARCH_PROVIDER` accepts exactly `auto`, `exa`, `keenable`, and `youcom`; unset or empty defaults to `auto`, and credentials never switch the selection. Explicit providers retain their direct remote entries and native tools.

In `auto`, Core resolves an absolute local `websearch` command to `mcp-servers/search-proxy/index.mjs`. The self-contained six-module Proxy uses Node.js built-ins only and is shared by OpenCode, Codex, and DSH. It exposes generic `search` and single-URL `fetch` and initially follows Exa → Keenable → You.com, with at most one attempt per provider per call and only after fallback-eligible failures. After a fallback-eligible Exa failure, every later call in the same Proxy process uses Keenable → You.com → Exa until the Proxy is recreated; this memory-only state is shared across sessions using that process, is not session-scoped or persisted, and has no cooldown. Successful empty results, auth/permission/parameter/non-retryable failures, and caller cancellation never fall back or change the order. Each backend attempt has a 30-second budget including lazy initialization and the tool call, giving a full three-attempt call an approximate 90-second backend upper bound; there is no fourth attempt or model-driven failover. Responses preserve readable backend content and provider/fallback metadata. Existing Exa and Keenable metadata is unchanged; You.com success after two eligible failures retains the first `fallback` and adds ordered `fallbacks` plus readable per-failure lines. Errors are bounded and redact credentials, queries, and target URLs. Only Proxy calls have this guarantee: a user-owned `websearch` or `youdotcom` server takes precedence without being wrapped, and host-native web tools outside OmAgents registration are excluded. Documentation must warn that eligible fallback can disclose the same query or URL to Exa, Keenable, and You.com; explicit `exa`, `keenable`, or `youcom` are direct single-provider opt-outs.

Explicit `youcom` registers `youdotcom` with optional `YDC_API_KEY`: keyed `https://api.you.com/mcp` uses `Authorization: Bearer <YDC_API_KEY>`, while keyless `https://api.you.com/mcp/free` sends no Authorization header and needs no OAuth flow. The [official You.com MCP documentation](https://you.com/docs/agents/mcp-server#choose-your-setup) advertises 100 queries/day for keyless use; keyless does not imply anonymous traffic or no provider logging. On You.com attempts, `you-search` forwards `query` and maps `maxResults` to `count`, while `you-extract` receives only `url`. Unsupported `objective` and `maxCharacters` are omitted only for that attempt without query rewriting or local response truncation.

## Loop Engine

Skills that process items iteratively (deep-research, remove-ai-slops, remove-deadcode, github-triage, tech-debt-audit) use a shared loop engine at `packages/core/skills/_shared/scripts/loop_engine.py`.

The loop engine provides a durable task queue stored in `.omagents/loops/<skill>/tasks.json` within the project directory. State survives context clearing and can be resumed.

**Commands:**

| Command | Usage |
|---------|-------|
| `init <skill> '<tasks_json>'` | Initialize task queue |
| `next <skill>` | Get next pending task (outputs JSON or `null`) |
| `complete <skill> <id> [result]` | Mark task complete |
| `fail <skill> <id> [error]` | Mark task failed (retries up to 3 times, then blocked) |
| `status <skill>` | Print stats (total/completed/pending/blocked) |
| `summary <skill>` | Print full task list with icons |
| `reset <skill>` | Clear task queue |
| `add <skill> '<task_json>'` | Add a task to existing queue |

**Task state machine:** `pending` -> (execute) -> `completed` (success) or `pending`/retry (fail, attempts < 3) or `blocked` (fail, attempts >= 3)

### Deep Research Storage

`packages/core/skills/deep-research/scripts/layout.py` is the single path resolver for all deep-research commands. For new runs, `--workspace` contains only public deliverables; internal plans, raw evidence, derived artifacts, checkpoints, and provenance live under `.omagents/deep-research/<run-id>/`. Main and pre-research loop keys are suffixed with the same run ID (`deep-research-<run-id>` and `deep-research-pre-<run-id>`), while the shared loop engine itself is unchanged.

Raw evidence and state are durable. Derived `artifacts/` are rebuildable but retained by default. New provenance always goes to `<run-dir>/logs/provenance.jsonl`; legacy root/`artifacts/` logs are combined on read. Reject new runs whose public workspace would contain the internal run or loop store (including the default project root) before any writes; require a separate child workspace. Existing legacy workspaces retain their original paths and unnamespaced loop keys—never migrate or delete them automatically.

Research pauses emit host-neutral `{ action: "dispatch_subagent", search_provider, description, prompt, name, cwd }` objects; batches wrap those singular objects in `dispatches`. Prompts carry the query, complete item details, every requested field's complete definition (name/description/requirements), the absolute plan path, current-date instructions, exclusive selected-provider search/fetch routing with exact OpenCode and Codex/DSH tool names, absolute evidence/validation paths, and the complete findings schema so fresh children never need to infer field IDs or inherit the parent's skill. Pre-research instructions carry the same provider selection and routing. In `auto`, shared and DSH skill rendering plus Python orchestration name only the generic Proxy tools (`websearch_search`/`websearch_fetch` for OpenCode and `mcp__websearch__search`/`mcp__websearch__fetch` for Codex/DSH), identify the Proxy as the exclusive research web route, and never ask children to perform fallback themselves; explicit providers retain their native mappings. The canonical structured `resume_command` uses the absolute Python and CLI paths; the former bare command is retained separately as `legacy_resume_command`. DSH translates each action to native asynchronous `subagent(description, prompt, cwd?)` without passing `name` as a tool argument; OpenCode V1/V2 and Codex retain their own native delegation forms through host rendering. Pending batches contain distinct queue rows, and gap analysis resumes the same run-scoped queue rather than creating a new run. Missing, unreadable, or malformed queues fail before gap/report stages, including corrupt task rows that are not objects or lack non-empty string `task_id`/`status`; only a valid queue with no pending tasks is drained. `layout.py` also resolves the queue state path so orchestration does not duplicate loop-store paths.

## Design Principles

1. **Prefer loop engineering over one-shot prompts.** When a skill involves processing multiple items (files, issues, categories, tasks), use the shared `loop_engine.py` to manage state. This provides durability (survives context clearing), retry logic, and a unified summary. Don't write a skill that says "scan everything and fix it" -- instead, build a task queue, process one item at a time, verify, and record the result.
2. **Infrastructure, not methodology.** OmAgents provides tools and capabilities. Development methodology (OpenSpec, gstack, etc.) is the user's choice. Don't bundle methodology into the plugin.
3. **Don't duplicate what the host provides.** OpenCode has LSP, edit tools, and search. Don't bundle alternatives. Instead, write skills that guide agents to use the right tool at the right time.
4. **Pin dependencies.** Superpowers is pinned to a commit. Don't unpin without testing.
5. **Keep README in sync with all languages.** README.md exists in 4 languages: English (README.md), Simplified Chinese (README.zh-cn.md), Japanese (README.ja.md), Korean (README.ko.md). Any change to README.md MUST be reflected in all language versions in the same commit. If a translation cannot be completed immediately, add `<!-- TODO: sync with README.md -->` at the top of the untranslated file.
6. **Analyze README impact on every change.** Before committing any change, ask: "Does this change affect what users see in README?" If yes -- new skill added, feature changed, installation steps modified, architecture updated -- update README.md (and all language versions) in the same commit. Don't let README go stale.
7. **Cross-platform compatibility.** Every code change must work on Linux, macOS, and Windows. Specifically:
   - **Venv paths**: Use `Scripts` on Windows, `bin` on Unix. Detect with `process.platform === "win32"`.
   - **Python command**: Use `python` on Windows, `python3` on Unix.
   - **PATH separator**: Use `;` on Windows, `:` on Unix.
   - **No bash-only scripts**: Hooks and helper scripts must be Node.js (`.js`), not bash (`.sh`). Use `node` to execute them.
   - **File paths**: Always use `path.join()` / `path.resolve()`, never hardcode `/` or `\\`.
   - **Executables**: On Windows, Python/pip executables have `.exe` extension (e.g., `python.exe`, `pip.exe`).

## Common Mistakes to Avoid

1. **Don't reference `templates/` as a root-level directory.** Templates are in `packages/core/skills/deep-research/templates/`.
2. **Don't claim tools are "pre-installed".** Only `jinja2` is auto-installed. Others are on-demand.
3. **Don't duplicate venv path info.** The `agents-python-tools` skill covers this. Reference it.
4. **Don't unpin superpowers.** It's pinned to a commit for stability.
5. **Don't add `templates/` to project structure diagrams.** It doesn't exist at root.
6. **Don't forget `.opencode/` has its own `.gitignore`** that excludes `node_modules`, `package.json`, and `package-lock.json`. OpenCode itself auto-generates these (it installs the `@opencode-ai/plugin` SDK into `.opencode/` when loading project plugins) — they are host artifacts and must not be committed.
7. **Don't confuse bundled skills with superpowers skills.** OmAgents has 18; superpowers has 15. They're registered separately.
8. **Don't change README.md without updating all language versions.** README exists in 4 languages (EN, ZH-CN, JA, KO). All must be updated in the same commit.
9. **Don't commit without checking README impact.** If your change adds a skill, changes a feature, or modifies installation steps, update README first.
10. **Don't put non-plugin scripts in `.opencode/plugins/`.** OpenCode auto-discovers and loads EVERY `.js` file in the project's `.opencode/plugins/` directory as a plugin, calling exported functions. A CLI script there (this broke startup when developing in this repo — see v0.9.1) crashes plugin init. CLI entry scripts live in each host package's `bin/` directory; only true plugin files belong in `.opencode/plugins/`.
11. **Don't point package `main` at the CLI wrapper.** OpenCode imports the plugin via `main`; module-level `process.argv` dispatch (plus `process.exit`) in that file kills the host process (this broke `opencode run` for npm installs of 0.7.0–0.9.1 — see v0.9.2). `main` must be the plugin entry (`packages/opencode/src/index.js`); only `bin` may point at the CLI wrapper.
12. **Don't export a bare function as `default` from `.opencode/plugins/*.js`.** OpenCode V2 requires the default export to be a `{ id, setup }` descriptor object and hard-fails the plugin otherwise (`PluginModule.LoadError`). Keep the dual shape `{ id, server, setup }`: `server` is the V1 plugin function, `setup` the V2 one. V1 hosts may invoke exported functions (including `setup`) with a V1-shaped ctx — guard V2 entry points by checking V2-only domains (e.g. `typeof ctx.session?.hook === "function"`) and return quietly.
13. **Don't import `@opencode/plugin` (V2 SDK) or `@opencode-ai/plugin` (V1 SDK) in plugin code.** The dual entry point is a plain object; importing a host SDK package breaks the other runtime. superpowers does the same.
14. **Don't run project pip with the base overlay enabled or auto-delete either venv.** Project dependencies must use `project-venv.js pip` (`OMAGENTS_PROJECT_ONLY=1`). Do not use `--system-site-packages` as a base-venv inheritance mechanism. Existing base/project environments are repaired only with explicit user confirmation.
15. **Don't assemble deep-research paths ad hoc or write internal files into `--workspace`.** Use `layout.py` and the absolute paths in dispatch JSON. Only final deliverables belong in the public workspace; legacy workspaces must not be migrated implicitly.
