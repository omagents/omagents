# Deep Research Storage Separation Design

Date: 2026-11-12
Status: Implemented and verified (90/90 Node tests, 11/11 Python layout/provenance tests)

## Purpose

Separate user-facing research deliverables from the durable state, evidence, logs, and derived files needed to execute, resume, audit, and reuse a deep-research run.

The current workspace mixes these concerns. Some paths also disagree between commands: early provenance events can be written to the workspace root while later events use `artifacts/`, and `run-all` writes `gap_report.json` to the root while other commands prefer `artifacts/gap_report.json`.

## Goals

1. Keep `--workspace` as the directory users open to consume final deliverables.
2. Store every standard non-deliverable for a new run under the project `.omagents` directory.
3. Isolate concurrent and historical research runs so their loop queues cannot overwrite one another.
4. Preserve raw evidence and curated inputs for resume, audit, and explicit future reuse.
5. Use one canonical path per file within a run.
6. Keep existing workspaces resumable without automatically moving or deleting user files.

## Non-Goals

- No automatic global research cache or implicit mixing of evidence across topics.
- No automatic migration, cleanup, or deletion of existing workspaces.
- No new migration command in this change.
- No new built-in generator for `summary.md`, `execution_roadmap.md`, `tco_model.md`, or other topic-specific documents.
- No redesign of the shared loop engine; deep research will namespace its existing loop keys instead.

## Approved Directory Layout

```text
<project>/
├── <workspace>/                         # User-facing deliverables only
│   ├── README.md                        # Human-readable deliverable index
│   ├── report.md
│   ├── summary.md                       # When actually produced
│   ├── execution_roadmap.md             # When promoted as a deliverable
│   └── tco_model.md                     # When promoted as a deliverable
│
└── .omagents/
    ├── deep-research/
    │   └── <run-id>/
    │       ├── plan.json
    │       ├── pre_research.json
    │       ├── pre_research_curated.json# Optional curated input
    │       ├── pre_findings/
    │       ├── findings/
    │       ├── artifacts/
    │       │   ├── findings_merged.json
    │       │   ├── gap_report.json
    │       │   ├── audit_report.json
    │       │   ├── report_raw.md
    │       │   └── package.json
    │       ├── state/
    │       │   ├── orchestration_state.json
    │       │   └── pre_research_state.json
    │       └── logs/
    │           └── provenance.jsonl
    └── loops/
        ├── deep-research-<run-id>/
        │   └── tasks.json
        └── deep-research-pre-<run-id>/
            └── tasks.json
```

`artifacts/` contains derived, generally regenerable files; it is not an automatic-deletion cache. Raw findings, curated inputs, run state, and provenance are durable and must not be cleaned as temporary data.

| `README.md` | Deliverable index | Workspace root | Regenerated by packaging |
| `execution_roadmap.md`, `tco_model.md` | Topic-specific draft or deliverable | `artifacts/` while draft; workspace root when delivered | Agent/user decision |
| `plan.json` | Research definition and resume input | Run root | Durable |
| `pre_research.json` | Consolidated reusable pre-research input | Run root | Durable |
| `pre_research_curated.json` | Optional curated authoritative input | Run root | Durable; never treat as cache |
| `pre_findings/` | Raw pre-research evidence | Run root | Durable |
| `findings/` | Raw research evidence | Run root | Durable |
| `findings_merged.json` | Derived evidence view | Run `artifacts/` | Rebuildable; retained by default |
| `gap_report.json` | Derived gap analysis | Run `artifacts/` | Rebuildable; retained by default |
| `audit_report.json` | Derived integrity audit | Run `artifacts/` | Rebuildable; retained by default |
| `report_raw.md` | Pre-polish recovery copy | Run `artifacts/` | Retained by default |
| `package.json` | Machine-readable run manifest | Run `artifacts/` | Regenerated by packaging |
| `orchestration_state.json` | Pipeline checkpoint | Run `state/` | Durable for resume |

| Loop `tasks.json` | Task queue and retry state | Existing loop root, namespaced by run | Durable for resume |

## Components

### 1. Central path resolver

Add one small Python path module shared by all deep-research scripts. It will resolve:

- Project root, defaulting to the invocation working directory, matching the existing loop-engine assumption.
- The absolute public workspace path from `--workspace`.
- A stable, filesystem-safe run ID consisting of the workspace slug and a short hash. The hash uses the project-relative workspace path when possible, so moving the whole project does not invalidate resume state.
- The internal run root at `<project>/.omagents/deep-research/<run-id>`.
- Every canonical input, evidence, derived, state, log, and deliverable path.
- Namespaced loop keys for new runs.

All commands and agent instructions must consume this resolver instead of assembling their own workspace-relative paths.

### 2. Legacy layout detection

A run uses the new layout when its resolved internal run directory contains new-layout state or a plan. Otherwise, an existing workspace containing legacy files such as `plan.json`, `pre_research_state.json`, or `orchestration_state.json` uses legacy mode.

New runs always use the new layout. Legacy runs keep their existing locations so `--resume` continues to work without file movement. Legacy loop keys remain `deep-research` and `deep-research-pre`; new keys include the run ID.

Readers that historically accepted both root and `artifacts/` locations retain those fallbacks. Legacy provenance loading must read both root and `artifacts/provenance.jsonl` when both exist, because earlier versions could split one timeline across those files. New writes have exactly one canonical destination.

### 3. Pipeline and individual commands

Update the unified CLI, orchestrator, pre-research helper, synthesis, gap analysis, audit packaging, and agent-facing instructions to use the same resolved layout.

The pipeline data flow becomes:

1. Create the public workspace and internal run directory.
2. Write pre-research checkpoints, raw pre-findings, and consolidated pre-research data internally.
3. Create and refine the internal plan.
4. Write raw findings internally and record task state in the run-specific loop queue.
5. Write merged findings and gap analysis to internal `artifacts/`.
6. Generate `report.md` in the public workspace and back up the pre-polish report internally.
7. Audit into internal `artifacts/`.
8. Package the internal manifest and generate a workspace-root README linking only public deliverables.

Standalone `plan`, `scan`, `merge`, `gaps`, `report`, `polish`, `audit`, `package`, `provenance`, and `status` commands must resolve the same paths as `run-all`.

### 4. Custom deliverables

Topic-specific Markdown files are not classified by extension. Drafts belong in internal `artifacts/`; a document is written or copied to the workspace root only when the agent intends it for delivery. Packaging may index Markdown deliverables already present in the workspace but must not move, delete, or rewrite their content.

Cross-run reuse is explicit: a future run may read an earlier run's `pre_research.json` or curated input through an explicit path. Runs must not share writable evidence files.

## Error Handling and Safety

- Fail with a clear error if a requested legacy or new-run input is missing; do not silently create a second run root during resume.
- Reject a new run before writing when its public workspace would contain the internal run or loop store (including the default project-root workspace); require a separate child workspace while preserving genuine legacy root workspaces.
- Treat required plan/checkpoint JSON as strict object inputs with clear errors; keep tolerant parsing only for optional derived reports.
- Supply exact output paths, shell-specific quoting, and structured resume argv in agent instructions; URL-encode public Markdown destinations.
- Do not auto-migrate or delete old files.
- Do not delete internal `artifacts/` after successful reporting.
- Create parent directories before writing and use `pathlib` paths throughout.
- Keep all paths usable on Linux, macOS, and Windows; sanitize run IDs and never interpolate unquoted paths into shell commands in generated instructions.
- When both canonical and legacy derived files exist in legacy mode, preserve the established preference for `artifacts/` while retaining root fallback.
- New provenance writes must not depend on whether `artifacts/` already exists.

## Acceptance Criteria

- A new completed run leaves only user-facing deliverables in `--workspace`.
- All standard non-deliverables are under the resolved run directory, except the existing shared loop store, whose keys are run-specific.
- The same `--workspace` resumes the same internal run from the same project root.
- Two workspaces can run concurrently without queue or artifact collisions.
- Existing workspaces remain readable and resumable without automatic file movement.
- Provenance and gap analysis each have one canonical new-run path and defined legacy-read behavior.
- All new and existing tests pass.
